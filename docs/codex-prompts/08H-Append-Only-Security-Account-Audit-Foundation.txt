GOAL
Add a PostgreSQL append-only audit foundation for security-sensitive account-management actions, and atomically record successful staff-account creation performed through the existing authorized Clinic Administrator workflow. This phase intentionally precedes Supabase privileged provisioning.

APPROVED SECURITY MODEL
- Audit data is server-generated and append-only.
- Routine application code may INSERT audit rows but must not UPDATE or DELETE them.
- The database must enforce immutability with a trigger that rejects UPDATE and DELETE attempts.
- Audit entries must not contain passwords, bearer tokens, refresh tokens, cookies, authorization headers, database connection strings, Supabase service-role keys, or other secrets.
- Audit metadata is generated from trusted server-side values, never copied wholesale from request bodies.
- Successful staff-account creation is recorded in the same PostgreSQL transaction as app_users/user_roles/user_branches writes.
- If the transaction fails, neither the staff account nor a false success audit entry may remain.
- Failure-event capture may be added later as a separate out-of-transaction security-event path; 08H must not invent a misleading success event for rolled-back work.
- No Supabase project, service-role credential, or Admin API call is introduced in 08H.
