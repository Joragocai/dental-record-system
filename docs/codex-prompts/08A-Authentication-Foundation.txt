GOAL
Establish a secure backend-first authentication foundation for future protected V2 routes using Supabase Auth bearer access tokens, while keeping the current V1 routes and runtime behavior unchanged until protected route integration is explicitly approved.

SCOPE
1. Verify branch, sync state, and clean working tree before editing. Do not perform Git write operations.
2. Follow README.md, AGENTS.md, current-system-audit.md, v2-migration-map.md, and patient-cutover-readiness.md.
3. Build new V2 authentication source in TypeScript.
4. Add lazy server-only auth configuration for Supabase URL, publishable key, expected JWT audience, and request timeout. Missing auth configuration must not break the existing V1 app merely by importing modules.
5. Add strict Authorization Bearer header parsing. Missing and malformed credentials must be distinguishable and must never echo the token.
6. Add a provider-independent access-token verifier interface and a minimal authenticated-principal type. Do not treat Supabase/Postgres `role` as the clinic application role; RBAC is deferred.
7. Add a Supabase verifier using the official authenticated user endpoint (`GET /auth/v1/user`) with the publishable key plus Bearer access token and built-in `fetch`. Do not implement JWT cryptography manually.
8. Validate the verified provider response at runtime before trusting identity fields.
9. Map invalid credentials, provider-unavailable failures, malformed provider responses, and configuration failures to safe typed authentication errors that do not expose SQL, URLs containing secrets, bearer tokens, provider response bodies, or stack details.
10. Add a small internal authentication boundary that future Express middleware/controllers can call. Do not wire it into current V1 routes in this task.
11. Update `.env.example` with placeholder-only auth variables needed by this foundation. Do not add or require the Supabase service-role key for access-token verification.
12. Add focused tests for config parsing, bearer parsing, successful verified identity mapping, invalid tokens, audience mismatch, provider failure, malformed response, and safe-error behavior.
13. Add an explicit auth test script without introducing new dependencies.
14. Document architecture, security properties, current non-cutover state, and next blockers.
15. Update the migration map only as needed for the new auth foundation.
