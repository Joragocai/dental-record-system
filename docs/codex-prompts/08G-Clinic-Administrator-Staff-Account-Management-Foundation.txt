GOAL
Allow an authenticated, active, authorized Clinic Administrator to create a pending clinic staff application record with approved operational role(s) and branch assignment(s), transactionally in PostgreSQL, while preventing self-elevation and preventing creation of Patient, Clinic Administrator, or System Administrator roles through this routine staff workflow.

APPROVED PRODUCT DECISIONS
- Staff cannot self-register.
- Clinic Administrator initiates staff account creation.
- Staff permanent passwords are never selected or known by the Clinic Administrator.
- Technical Supabase account creation/invitation remains a later backend-only provisioning step.
- No Supabase service-role key is introduced in 08G.
- Routine staff creation may assign only PERSONNEL and DENTIST roles.
- Creating another CLINIC_ADMINISTRATOR, SYSTEM_ADMINISTRATOR, or PATIENT identity is a separate privileged workflow and is not allowed here.
- Every created staff record starts with status `pending` and `auth_user_id = NULL`.
- At least one operational role and one valid clinic branch are required.
- Role and branch assignments are written in the same PostgreSQL transaction as the pending application user.
- The caller must pass the already-proven RBAC boundary and have both `staff_account.create` and `role_assignment.approve`.

SCOPE
1. Verify a clean synchronized branch before editing. Do not perform Git write operations.
2. Do not add or modify PostgreSQL schema migrations unless an actual schema gap is discovered. Reuse Phase 08D tables `app_users`, `roles`, `user_roles`, and `user_branches`.
3. Add a typed staff-account write repository with parameterized PostgreSQL operations for:
   - checking an existing email case-insensitively;
   - validating requested role codes against existing seeded roles;
   - validating requested branch UUIDs against existing branches;
   - inserting a pending `app_users` row with nullable `auth_user_id`;
   - inserting role assignments;

4. Add a transactional StaffAccountManagementService that:
   - validates and normalizes display name and email;
   - accepts only PERSONNEL and DENTIST role codes;

   - validates all branch IDs as UUIDs before DB mutation;
   - generates an application user UUID;
   - creates the user + role assignments + branch assignments atomically;
   - returns only a safe pending-account summary;
   - never returns/stores a password, provider token, refresh token, or service secret.
5. Add safe typed staff-account errors and translate PostgreSQL/unknown persistence failures without leaking connection details. Duplicate email should produce a safe conflict response.
