GOAL
Complete the next cross-cutting audit foundation required by the V2 architecture: request correlation, Clinic Administrator audit review/export, and audit-of-audit-access, while keeping domain-specific clinical/financial audit events aligned with the later protected vertical slices that actually own those operations.

APPROVED BASELINE / DESIGN CONSTRAINTS
- audit_events remains append-only.
- Existing migrations 0001–0008 must never be edited.
- Clinic Administrator may review the complete clinic audit trail.
- System Administrator must not receive routine access to the complete clinic audit trail.
- Clinic Administrator role alone still does not imply clinical record access.
- Audit metadata must not contain passwords, access/refresh tokens, cookies, authorization headers, provider secrets, connection strings, or unnecessary health information.
- Audit failures must not replace the primary application/security error.
- Browser-to-Supabase authentication events must not be falsely labeled as backend-observed login events.

IMPLEMENTATION SCOPE

1. PostgreSQL migration 0009
- Add nullable audit_events.request_id UUID.
- Add an index supporting request-id correlation.
- Add GLOBAL permission audit.read.
- Add GLOBAL permission audit.export.
- Grant audit.read and audit.export to CLINIC_ADMINISTRATOR only.
- Do not grant complete clinic audit access to SYSTEM_ADMINISTRATOR.

2. Request correlation
- Add a server-generated UUID request identifier for Express API requests.
- Store it in trusted response/request locals.
- Return it in a safe X-Request-ID response header.
- Do not trust arbitrary client data as audit identity.
- New HTTP-generated audit events should carry the request ID when available.
- Existing CLI/bootstrap events may continue with request_id = NULL.

3. Audit repository read boundary
- Keep the existing insert boundary.
- Add read-only methods needed for:
  - paginated audit-event listing;
  - audit-event detail by UUID;
  - bounded export query.
- Use parameterized SQL.
- Use deterministic newest-first ordering.
- Apply safe maximum page/export limits.

4. Audit review service
- Add typed validation/normalization for supported filters.
- Initial filters may include action, outcome, branch UUID, actor application-user UUID, target type, date/time range, and bounded limit.
- Invalid UUID/date/filter inputs must fail before PostgreSQL access.
- Do not expose provider secrets or hidden database details in errors.

5. Protected HTTP routes
Implement the documented V2 route surface:
- GET /api/audit-events
- GET /api/audit-events/:auditEventId
- POST /api/audit-events/export

Requirements:
- Authenticate first.
- Resolve active application user.
- Resolve authorization.
- list/detail require audit.read.
- export requires audit.export.
- Clinic Administrator owner account may access through its CLINIC_ADMINISTRATOR role.
- DENTIST alone, PERSONNEL, PATIENT, and SYSTEM_ADMINISTRATOR must be denied by default.

6. Audit the audit trail
- Successful list/detail review must append AUDIT_LOG_VIEWED.
- Successful export must append AUDIT_LOG_EXPORTED.
- These events must record trusted actor IDs and request ID.
- Metadata must be minimal, e.g. view type, bounded result count, and safe filter names/values where appropriate.
- Audit viewing/export events themselves remain append-only.
- The event being written for a list view should not mutate or rewrite the already-returned audit history.

7. Export behavior
- Produce a bounded server-generated CSV response for authorized Clinic Administrator use.
- Include only audit fields approved for the complete clinic audit view.
- Do not export passwords, tokens, secrets, connection strings, or raw authorization data.
- Do not introduce private object storage dependency in Phase 09.

8. Selected authorization-denial audit coverage
- Add best-effort AUTHORIZATION_DENIED auditing only where a valid authenticated application user has already been resolved and a sensitive permission check is denied.
- Include permission code, safe branch context when relevant, and request ID.
- Failure to write this secondary audit event must never replace the original 403 denial.
- Do not audit malformed/invalid bearer-token contents into PostgreSQL.

9. Tests

- migration 0009 ordering/checksum;
- request ID generation and response header;
- audit.read/audit.export role grants;
- Clinic Administrator list/detail/export success;
- Dentist-only, Personnel, Patient, and System Administrator denial;

- AUDIT_LOG_VIEWED and AUDIT_LOG_EXPORTED events;

- authorization-denial audit is best-effort and does not replace the primary 403;
- append-only UPDATE/DELETE protection still holds;
