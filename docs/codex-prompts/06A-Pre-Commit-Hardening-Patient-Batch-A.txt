HARDENING ISSUE 1 — PATIENT + LEGACY MAP MUST BE ATOMIC

Current migrateLegacyPatient() performs the patient insert and
legacy_patient_identity_map insert as separate operations.

Make one patient migration unit transactional so that:
- patient row + legacy identity mapping succeed together; or
- neither remains if either operation fails.

Use the existing PostgreSQL transaction foundation.
Do not add a generic transaction framework.

Add tests proving:
- identity-map insert failure rolls back the patient insert;
- patient insert failure leaves no mapping;
- successful migration persists both.

Do not merely document that callers should use a transaction while the
actual integration path still calls the non-transactional sequence.

HARDENING ISSUE 2 — RERUN / IDEMPOTENCY SAFETY

The current mapping path generates a new random UUID and inserts blindly on
each call.

The Phase 06A specification requires safe rerun/idempotency behavior.

Implement a narrow, explicit rerun policy based on the legacy identity keys.

Requirements:
- rerunning the same fictional legacy patient must not create a second patient;
- rerunning must not create a second mapping;
- conflicting legacy identity / patient-code mappings must fail clearly;
- the behavior must be deterministic and tested;
- do not silently overwrite mismatched migrated data.

A safe no-op/reuse of an existing matching mapping is acceptable.
A deliberate pre-write conflict failure is also acceptable if it preserves
one-to-one identity and the migration harness can safely be rerun.
Choose the smallest behavior that satisfies the Phase 06A contract.

Add a LIVE PostgreSQL integration assertion for the second run.

HARDENING ISSUE 3 — FULL FIELD-LEVEL PARITY

The current live integration test checks only a subset of the Patient fields.

Strengthen the fictional parity test so it verifies the complete mapped
Patient record, not only:
- patient code
- branch
- name
- a few condition flags

Requirements:
- every persisted V1 Patient field represented by Batch A must be accounted for;
- generated V2 UUID may be compared through mapping rather than to a source value;
- branch_location is validated through the explicit fictional mapping rule;
- all condition fields are checked after integer -> boolean conversion;
- date/timestamp transformations are checked;
- nullable/optional fields are checked;
- source row count / target row count / identity-map count are checked;
- no source row silently disappears;
- no extra target patient is created.

Prefer a reusable expected-transformation/parity helper instead of dozens of
unrelated hand-written assertions if that keeps the test maintainable.

HARDENING ISSUE 4 — EMPTY STRING / NULL RULE MUST MATCH THE APPROVED MAPPING

The pre-edit mapping matrix states that optional blank strings are normalized
to NULL in V2, but normalizeOptionalString() currently preserves an empty
string as "".

Resolve this inconsistency.

Unless the committed Phase 06A source of truth says otherwise:
- null/undefined -> NULL
- empty or whitespace-only optional strings -> NULL
- meaningful text -> preserve the meaningful value

Do not apply this normalization to required fields unless explicitly approved.

Add focused tests using the existing fictional fixture fields that currently
contain empty strings.

Update the architecture note only if needed so documentation and code say the
same thing.
