GOAL
Align the V2 data model and architecture with the approved single-clinic, multi-branch operating model without introducing unnecessary scheduling or branch-management complexity.

APPROVED PRODUCT DECISIONS
- The system represents one clinic organization that may have one or many branches.
- Future branches must be addable without redesigning the schema.
- Branches use UUID identity internally plus a unique branch code and human-readable branch name.
- Clinic Administrator authority is clinic-wide for administrative/business responsibilities and is not limited to one branch assignment.
- Dentist and Personnel users may be associated with multiple branches and may work together or separately depending on schedule.
- user_branches represents allowed/associated branch membership; it is not a permanent employee home-branch lock.
- Actual branch of service is stored on branch-specific operational transactions.
- Patients belong to the clinic as a whole. A patient does not need a duplicate patient record when visiting another branch.
- patients.branch_id is retained for compatibility as the registration/origin branch context and must not be interpreted as patient ownership.
- Appointments already store branch_id.
- Treatments must store branch_id for the branch where care occurred.
- Legacy/mock treatment migration may deterministically use the migrated patient's registration/origin branch as a historical migration fallback only; future V2 treatment creation must supply the actual service branch explicitly.
- Existing free-text dentists data remains a legacy parity field for now. Authenticated dentist/user linkage for treatment creation is deferred to the protected Treatment vertical slice.
- Do not add a clinics table for the current single-clinic product.
- Keep the design intentionally simple; do not build staff calendars, shift scheduling, branch CRUD UI, or automatic branch assignment in this phase.
