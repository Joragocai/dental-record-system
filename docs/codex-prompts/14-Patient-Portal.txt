SECURITY NON-NEGOTIABLES
1. No public self-registration or self-claiming a patient using email, phone, patient code, birthday, or provider user metadata alone.
2. A clinic-authorized and auditable verification/approval step must explicitly choose the existing patients.id to be linked before the managed Supabase Auth invitation. Define a documented patient-identity verification procedure before 14A write implementation.
3. A normal patient has only the PATIENT role. No routine staff/Clinic Administrator/System Administrator roles or branch grants; patient ownership is clinic-wide and is NOT inferred from patients.branch_id.
4. Every /api/me handler authenticates, resolves an active app_user, validates an active verified patient-account link, authorizes the OWN operation on the backend, and scopes SQL by that resolved patient UUID. Never trust patientId, recipientUserId, provider role claims, or staff-settable client fields as ownership proof.
5. Existing generic OWN checks stay fail-closed until a specifically tested patient-own evaluator is introduced. Do not change requirePermission/requireBranchPermission to allow arbitrary OWN grants.
6. Wrong-account and unlinked-record access must not leak record existence, contact details, source IDs, clinical data, or private object paths; use indistinguishable not-found/denied semantics when appropriate. Do not expose staff notes, internal treatment notes, draft/unpublished records, financial internals, or audit event metadata to patients.
7. All account creation/linking, invitation, activation, revocation, sensitive reads, and appointment requests must have bounded request-correlated append-only audit records with no passwords, tokens, secrets, or unnecessary clinical details.
8. Server-only Supabase privileged credentials; TLS verification, staging isolation, branch RBAC, private Storage, and disabled email worker must not be weakened.
9. Use fictional A/B linked patients in an isolated throwaway TEST_DATABASE_URL for integration tests. Never manufacture an active Supabase staging identity by directly inserting into PostgreSQL. Hosted two-identity QA remains a distinct Phase 19 gate.
