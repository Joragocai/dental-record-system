NEW MIGRATION PRINCIPLES

The repository must clearly adopt these principles:

1. V1 IS A REFERENCE IMPLEMENTATION, NOT THROWAWAY CODE
   - Keep stable V1 code available while the corresponding V2 capability is not yet proven.
   - Use V1 code, tests, and current behavior as evidence for what must be preserved.

2. DO NOT BULK-CONVERT FOR THE SAKE OF FILE EXTENSIONS
   - "Zero JavaScript files" is not a milestone by itself.
   - Do not convert legacy code that will soon be structurally replaced for PostgreSQL, auth/RBAC, private storage, or other V2 architecture.

3. REUSE GOOD CODE
   - Already-clean migrated TypeScript should remain and be reused when it fits V2.
   - Pure helpers and stable business logic may be migrated directly if reuse is cheaper and safer than replacement.

4. REPLACE ARCHITECTURE THAT WILL CHANGE HEAVILY
   - Legacy persistence/database code should not be converted to TypeScript merely to be rewritten again for PostgreSQL.
   - Large legacy services/routes/pages should be assessed based on future V2 fit, not extension.

5. BUILD V2 IN VERTICAL DOMAIN SLICES
   - Work feature/domain by feature/domain.
   - Example domains:
     - Patient
     - Treatment
     - Appointment
     - Attachments
     - Dashboard/reporting
     - Backup/export
     - Authentication/RBAC
     - Audit
     - Patient Portal
     - Finance

6. EACH V2 SLICE SHOULD USE THE TARGET ARCHITECTURE WHEN THAT FOUNDATION EXISTS
   - New V2 production code is TypeScript by default.
   - PostgreSQL becomes the target persistence layer after PostgreSQL Foundation is established.
   - Do not create unnecessary intermediate TypeScript+SQLite rewrites of code that is about to be replaced.

7. PRESERVE PARITY BEFORE RETIRING LEGACY PATHS
   - Do not delete a V1 implementation merely because a V2 file exists.
   - Retire legacy code only after:
     - required behavior is covered;
     - data migration/parity is verified;
     - targeted tests pass;
     - applicable regression/integration tests pass;
     - the new runtime path is confirmed active.

8. NO BIG-BANG REWRITE
   - Do not create a separate full application and wait until the end to test it.
   - Replace capabilities incrementally with reviewable, reversible slices.

9. CLASSIFY LEGACY/MIGRATED FILES BY FUTURE ROLE
   Use these categories:

   KEEP
   - already-good code that fits V2 with little/no architectural change.

   ADAPT
   - useful existing code that should remain but will later need V2 integration changes.

   REPLACE
   - code whose architecture is expected to change materially; do not spend effort fully converting it first.

   BRIDGE
   - temporary JS/TS/runtime interoperability file needed during transition.

   RETIRE-LATER
   - legacy implementation that remains as reference/runtime fallback until V2 parity is proven.

10. TEST BUSINESS BEHAVIOR, NOT INTERNAL IMPLEMENTATION IDENTITY
    - V2 does not need to reproduce the same internal function layout.
    - It must preserve approved externally observable behavior and data semantics.
    - Example:
      - V1 can use SQLite and readable IDs internally.
      - V2 can use PostgreSQL + UUIDs internally.
      - User/business behavior must still satisfy the approved requirements.
