GOAL
Implement a trustworthy clinic billing, collections, receivables, expenses, payables and daily closing system without treating legacy treatment.amount_paid/balance as an accounting ledger.

SUBPHASES
15A — Invoice draft & exact financial arithmetic foundation (current)
- Draft invoices from an existing treatment verified server-side, preserving treatment and billing branch.
- PostgreSQL invoice/invoice_items schema with strict monetary constraints and patient/branch composite FKs.
- Patient-specific Senior Citizen/PWD discount NOT doubled: exactly one 20% basis, validate authoritative treatment snapshot; incompatible or previously-paid legacy treatments stop for reconciliation.
- Money as exact integer cent arithmetic with NUMERIC(12,2) storage, no binary floating point for financial totals.
- Narrow finance.invoice.draft/read BRANCH grants for clinical/operational staff; finance.admin.read GLOBAL for Clinic Administrator but no admin billing route yet; System Administrator and PATIENT no broad financial grants.
- POST /api/invoices draft and GET /api/invoices/:invoiceId protected, transactional append-only audit; no financial posting, receipt number, invoice finalization, payables or patient balance exposure.
- Migration 0016 appended, unapplied. Unit/route/staging regressions + isolated real PostgreSQL tests pending safe TEST_DATABASE_URL.

15B — Internal finalization and audited void (LOCAL IMPLEMENTATION COMPLETE; NO OFFICIAL ISSUANCE; ADJUSTMENTS/REAL DB TESTS OUTSTANDING)
- Locally implemented `0017_internal_invoice_lifecycle.sql`, internal `INT-YYYY-NNNNNN` reference allocation, branch-scoped POST `/api/invoices/:invoiceId/finalize` and `/api/invoices/:invoiceId/void`, mandatory void reason, database immutability triggers, status events and audit. No statutory invoice/official receipt number is issued; clinic/accountant numbering and tax policies still require approval.
- Immutable finalized financial documents; reversal and correction only through audited compensating actions.
- Enforce sums of items, serial collisions, safe concurrent finalization, and finalized-row mutation prevention.

15C — Payments / allocations / reversals / refunds (LOCAL IMPLEMENTATION; UNAPPLIED MIGRATION AND ISOLATED POSTGRESQL GATES)
- Local migration `0018_payment_allocation_refund_ledger.sql` and backend transaction services/routes implement multi-invoice allocation, invoice row locking, idempotency, immutable ledger events, controlled reversal, allocation-bound refunds and append-only audits. Receipt numbers intentionally remain NULL: these are internal simulated/test records, NOT official receipts. Real PostgreSQL concurrency, trigger behavior, refund rollback and legal/accountant sign-off remain outstanding.
- Payment methods Cash, GCash, transfer, cards, cheque and Other, cash-vs-digital separate.
- No official receipt issuance without clinic/accountant policy; do not mutate finalized payments.

15D — Collectibles / expenses / suppliers / payables (LOCAL BACKEND IMPLEMENTED; ISOLATED POSTGRESQL GATE OPEN)
- Locally implemented `/api/finance-operations/receivables` and `/receivables/followups`, deriving branch-owned unpaid finalized invoices from ledger balances with due-date aging and audited follow-up notes. No treatment.balance shortcut. Statement-of-account printing/export requires a separate reviewed UX scope.
- Locally implemented migration `0019_collectibles_expenses_payables.sql`: expense categories, branch-scoped suppliers, pending expense/bill creation, Clinic Administrator-only review, append-only idempotent approved payable payments, and protected `/api/finance-operations` routes. No default paid status on expense creation. Integration, real PostgreSQL concurrency, and browser UX remain outstanding.

15E — Daily finance, cash closing, statements, portal finance (LOCAL IMPLEMENTATION; POSTGRESQL AND ACCOUNTING GATES OPEN)
- Implemented local-only migration `0020_daily_finance_closing.sql`, branch-scoped ledger-derived daily summaries, explicit opening cash authorization, duplicate-protected closing submissions with actual-count/attestation and discrepancy reason, immutable reviewed closing snapshots, dual control (Clinic Administrator cannot approve own submission), and append-only events/audits. Direct expense payments are not modeled, so the summary labels this data unavailable rather than inventing an expense figure. Cash closing completeness and business timezone policy require accountant QA.
- Implemented patient OWN-scoped `/api/me/balance` and `/api/me/payments` with a separate patient portal finance page, based only on finalized invoices and patient-linked internal payment records. Historical treatments without approved invoices are intentionally excluded with an explicit note; no official receipts are issued.
- Implemented lazy loaded `/clinic-finance`, `/patient-finance` and permission-guarded audited `GET /api/finance/reports/daily` CSV. Real PostgreSQL testing, chart/timezone policy, clinic report completeness, finance UI UAT/accessibility, historical balance reconciliation and official accounting remain open security/release gates.

SECURITY AND RELEASE GATES

- No client-provided patientId, branchId, amount or discount may override trusted treatment snapshots.
- Separate draft-invoice reference from statutory invoice/official receipt number until approved by clinic accountant.
- Test safe transaction rollback, duplicates, cross-branch/mixed-role denials, cent math, no negative balances, audits.
- Keep all manual intervention in docs/deployment/patient-portal-staging-gate.md; live QA deferred to Phase 19.
- 15A completion does not imply full Phase 15 completion, staged availability or readiness to collect actual money.
- No Git commit, push, staging migration, deployment, provider action or real patient/financial data without approval.
