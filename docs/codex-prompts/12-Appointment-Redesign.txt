CORE BUSINESS MODEL

1. Patient identity
- Patients remain clinic-wide.
- An appointment branch is the location where that appointment occurs.
- A patient registered/originating at Branch A may have an appointment at Branch B without creating another patient.
- Phase 12 may expose only the minimal patient lookup needed for scheduling; broad Patient route/UI cutover remains separate.

2. Dentist/provider assignment
- Add a nullable Dentist application-user relationship to appointments.
- Requested/pending appointments may exist without a final assigned Dentist.
- A slot-reserving appointment must have an assigned active application user holding the DENTIST role and assigned to the selected branch.
- Dentist availability is global across branches: the same Dentist cannot occupy overlapping active slots at two branches.
- Do not create a permanent home-branch concept or staff shift tables.

3. Appointment timing
- Preserve appointment_date as PostgreSQL DATE and appointment_time as clinic-local wall-clock TIME.
- Default clinic scheduling timezone remains Asia/Manila.
- Add duration_minutes for slot-reserving appointments instead of relying on a separately editable end time.
- Workflow/event timestamps use TIMESTAMPTZ/UTC.
- Appointment time may remain unset while a request has no final time.
- A confirmed/slot-reserving appointment requires a valid start time and duration.

4. Stable V2 statuses
Store stable machine values and display friendly labels:
- requested
- pending_confirmation
- confirmed
- checked_in
- in_progress
- completed
- cancelled_by_patient
- cancelled_by_clinic
- no_show
- rescheduled

Migration compatibility for existing V2 rows:
- Scheduled -> confirmed
- Completed -> completed
- Cancelled -> cancelled_by_clinic because the V1 workflow had no patient self-service cancellation path
- No-show -> no_show

Do not silently preserve old display labels as the new persisted machine values.

5. Rescheduling and cancellation
- Cancellation never deletes an appointment.
- Rescheduling must preserve the original appointment and lineage rather than destructively erasing the prior slot.
- The preferred model is to mark the original appointment rescheduled and create/link a replacement appointment for the new schedule.
- Preserve who acted, when, reason when supplied, old/new schedule facts, and replacement lineage.
- A rescheduled/cancelled/completed/no-show appointment does not reserve an active slot.

6. Appointment history
Add an append-only appointment_history structure for business workflow history.
History should capture enough trusted server-side facts to reconstruct important changes, including:
- appointment UUID
- transition/action
- previous and new status
- previous and new date/time/duration/provider/branch when applicable
- actor application-user UUID when an authenticated clinic user performed the action
- cancellation/reschedule reason when supplied
- related replacement appointment UUID when applicable
- request ID correlation
- occurred_at timestamp

History is not a replacement for audit_events. appointment_history is the appointment business timeline; audit_events remains the security/compliance audit trail. Both should use server-observed facts.

Initial grant policy:

- PATIENT: no Phase 12 clinic appointment permission. OWN-scoped patient self-service is Phase 14.

The owner account continues to receive clinical appointment access through its separate DENTIST role, not by CLINIC_ADMINISTRATOR implication.

PHASE 12B — POSTGRESQL DOMAIN / CONFLICT SAFETY

Build new V2 TypeScript repository/service boundaries for:
- list/detail
- scheduling context
- minimal clinic-wide patient lookup for an authorized target branch
- availability
- create
- update non-state scheduling metadata where appropriate
- confirm
- reschedule
- cancel
- check-in
- start/in-progress
- complete
- no-show

Validation requirements:
- UUIDs validated before database access.
- Branch exists and actor has the required branch-scoped permission.
- Assigned Dentist is active, has DENTIST role, and has membership in the target branch.
- Date/time/duration rules are validated server-side.
- Past-time rules use clinic-local scheduling semantics.
- Invalid status transitions fail safely.
- Patient lookup for scheduling returns only minimal operational fields and must not become a broad unauthenticated Patient API.

Double-book prevention:
- Must be enforced in a PostgreSQL transaction, not only in React.
- For a slot-reserving write/update/reschedule, serialize conflict decisions for the Dentist/date in PostgreSQL (for example with a transaction-scoped advisory lock or another reviewed database-safe mechanism).
- Query overlapping active appointment intervals using start time + duration.
- Conflict checks apply across all branches for the same Dentist.
- Concurrent attempts for the same overlapping Dentist slot must result in only one successful reservation; the loser receives a safe 409-style conflict.
- requested/pending_confirmation rows do not have to reserve a Dentist slot until confirmation policy requires it.
- Do not rely on a simple start-time equality check because partially overlapping appointments must conflict.

Status-transition policy must be explicit and tested. Do not expose a generic arbitrary status mutation endpoint that bypasses workflow rules.

Every material write should persist appointment_history and the applicable audit event with the trusted request ID. Where practical, database state + history + audit should commit atomically.
