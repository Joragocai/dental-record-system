GOAL
Build a safe, authenticated, permission-driven landing experience for five distinct roles, supporting one Dentist + Clinic Administrator account without combining backend role definitions. Show only real authorized information backed by verified V2 endpoints. Separate provider authentication from server-owned app roles, current branch memberships and OWN-linked patient identity. No dashboard visibility is itself an authorization grant.

ARCHITECTURAL RULES
1. Implement new V2 dashboard page and services in TS/TSX, additive and focused. Keep the legacy branch untouched.
2. Secure default landing route must require a verified backend session; handle loading, 401/403, inactive account, no role and missing branches explicitly.
3. Derive role codes, permission codes/scopes and branch IDs on the server from current application authorization data. Do not trust client JWT custom claims or user-chosen roles/branch IDs as grants. Do not expose complete privileged policy/grant catalogs unless necessary; prefer a minimal server-provided navigation/action capability projection.
4. Distinguish GLOBAL clinic authority, BRANCH operations and OWN patient access. No universal dashboard aggregation of unrestricted records.
5. Users with multiple roles receive an authorized union of permitted cards but retain per-widget permission/branch checks; explicit denials and privileged safeguards override role union.
6. System Administrator is technical only: no patient names/clinical notes/attachments/finance or indirect leaks through error logs/metadata. Clinic Administrator does not inherit dentist clinical authority.
7. Never return actual patient records in dashboard context; fetch data only from specific protected APIs. Use approved statuses and clinic local dates/timezone for schedule queries.
8. No fake metrics, fabricated zeros, unchecked summaries, insecure placeholders, or calls to old anonymous V1 routes. Unsupported widgets are omitted or marked unavailable without counts.
9. Preserve audit of sensitive read actions, limit list sizes, implement pagination as needed, avoid cross-user caching and stale permission state after role revocation.
10. Functional workflow change, RBAC expansion, finance accounting/tax policy change, backup/restore implementation, or deployment requires separate approval.
