# V2 Append-Only Audit Foundation

## Status

Phase 08H establishes the first append-only security/account audit boundary before privileged Supabase staff provisioning is introduced.

## Purpose

The audit trail records security-sensitive actions using server-generated facts rather than browser-supplied audit claims. The first integrated event is successful Clinic Administrator staff-account creation.

```text
authenticated Clinic Administrator
  -> active application user
  -> RBAC authorization
  -> staff account transaction
  -> app_users + user_roles + user_branches
  -> STAFF_ACCOUNT_CREATED audit event
  -> COMMIT
```

If the staff-account transaction or audit insert fails, the transaction rolls back so a successful audit event cannot disagree with persisted account state.

## PostgreSQL Schema

Migration `0007_append_only_audit_foundation.sql` adds `audit_events` with:

- UUID event identity;
- application-user actor UUID;
- authenticated-provider UUID snapshot;
- action;
- target type and optional target UUID;
- optional branch UUID;
- `SUCCESS` or `FAILURE` outcome;
- JSONB metadata object;
- occurrence timestamp.

Indexes support actor/time, target/time, action/time, and chronological lookup.

The current staff-creation event uses:

```text
action      = STAFF_ACCOUNT_CREATED
target_type = APP_USER
target_id   = newly-created staff application user
branch_id   = null for multi-branch creation
outcome     = SUCCESS
```

Safe metadata contains only the normalized assigned role codes, normalized assigned branch UUIDs, and the resulting `pending` status.

## Append-Only Enforcement

PostgreSQL installs a `BEFORE UPDATE OR DELETE` trigger on `audit_events`. Routine UPDATE or DELETE attempts raise an error. Application code exposes only an insert repository for audit events.

This protects against ordinary application mutation. Database superusers/owners retain administrative capabilities outside the normal application path, so operational database access and backups remain part of the larger security model.

## Sensitive-Data Rules

Audit metadata is generated by backend services and is not copied wholesale from request bodies.

The audit service rejects metadata keys associated with secrets, including password, token, secret, authorization, cookie, service-role, and database/connection URL shapes. It also rejects obvious bearer credentials and PostgreSQL connection URLs in string values.

Audit rows must not store:

- passwords;
- bearer or refresh tokens;
- cookies or authorization headers;
- Supabase service-role credentials;
- PostgreSQL connection strings or database passwords.

## Staff Account Integration

`POST /api/staff-accounts` remains protected by authentication, active application-user resolution, and both `staff_account.create` and `role_assignment.approve`.

The route now passes the trusted actor UUIDs from `res.locals.applicationUser` separately from the request payload. `StaffAccountManagementService` records the successful audit event in the same PostgreSQL transaction as the pending staff account, role assignments, and branch assignments.

The external 201 response remains unchanged and does not expose audit internals, provider identifiers, permissions, passwords, or secrets.

## Failure Events

Phase 08I now uses the existing `FAILURE` outcome for selected staff-invitation failures. These failure events are written outside the failed provider/database operation using safe internal reason codes only. They never contain provider response bodies, email addresses, bearer tokens, connection strings, or Supabase secrets.

## Supabase Boundary

Phase 08I uses the audit service for `USER_INVITED` success/failure and `USER_ACTIVATED` success events. The provider invitation and PostgreSQL transaction cannot be one distributed transaction, so the backend attempts best-effort provider-user cleanup when local linkage/audit fails. A cleanup failure produces a reconciliation-required result rather than automatically linking a provider identity by matching email.
