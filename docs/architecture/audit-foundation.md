# V2 Append-Only Audit Foundation

## Status

Phase 08H established the append-only security/account audit boundary. Phase 09 extends that foundation with trusted HTTP request correlation, Clinic Administrator-only audit review/export, audit-of-audit-access, and best-effort authenticated authorization-denial events.

## Purpose

The audit trail records security-sensitive actions using server-generated facts rather than browser-supplied audit claims. The first integrated event is successful Clinic Administrator staff-account creation.

```text
authenticated Clinic Administrator
  -> active application user
  -> RBAC authorization
  -> staff account transaction
  -> app_users + user_roles + user_branches
  -> STAFF_ACCOUNT_CREATED audit event
  -> COMMIT
```

If the staff-account transaction or audit insert fails, the transaction rolls back so a successful audit event cannot disagree with persisted account state.

## PostgreSQL Schema

Migration `0007_append_only_audit_foundation.sql` adds `audit_events` with:

- UUID event identity;
- application-user actor UUID;
- authenticated-provider UUID snapshot;
- action;
- target type and optional target UUID;
- optional branch UUID;
- `SUCCESS` or `FAILURE` outcome;
- JSONB metadata object;
- occurrence timestamp.

Migration `0009_audit_review_request_correlation.sql` adds nullable `request_id UUID`, a request/time correlation index, GLOBAL `audit.read` and `audit.export` permissions, and grants both permissions only to `CLINIC_ADMINISTRATOR`. The migration explicitly removes those two complete-audit permissions from any other role if present. The development Supabase PostgreSQL database has migration 0009 applied and read-only verification confirms the UUID column, correlation index, GLOBAL permissions, and Clinic Administrator-only grants.

Indexes support actor/time, target/time, action/time, and chronological lookup.

The current staff-creation event uses:

```text
action      = STAFF_ACCOUNT_CREATED
target_type = APP_USER
target_id   = newly-created staff application user
branch_id   = null for multi-branch creation
outcome     = SUCCESS
```

Safe metadata contains only the normalized assigned role codes, normalized assigned branch UUIDs, and the resulting `pending` status.

## Append-Only Enforcement

PostgreSQL installs a `BEFORE UPDATE OR DELETE` trigger on `audit_events`. Routine UPDATE or DELETE attempts raise an error. Application code exposes only an insert repository for audit events.

This protects against ordinary application mutation. Database superusers/owners retain administrative capabilities outside the normal application path, so operational database access and backups remain part of the larger security model.

## Sensitive-Data Rules

Audit metadata is generated by backend services and is not copied wholesale from request bodies.

The audit service rejects metadata keys associated with secrets, including password/passphrase, token/JWT, secret, authorization, cookie, credential, API/access/client/private key, service-role, and database/connection URL shapes. It also rejects obvious bearer credentials, Supabase secret keys, private-key blocks, JWT-like values, and PostgreSQL connection URLs in string values.

Audit rows must not store:

- passwords;
- bearer or refresh tokens;
- cookies or authorization headers;
- Supabase service-role credentials;
- PostgreSQL connection strings or database passwords.

## Staff Account Integration

`POST /api/staff-accounts` remains protected by authentication, active application-user resolution, and both `staff_account.create` and `role_assignment.approve`.

The route now passes the trusted actor UUIDs from `res.locals.applicationUser` separately from the request payload. `StaffAccountManagementService` records the successful audit event in the same PostgreSQL transaction as the pending staff account, role assignments, and branch assignments.

The external 201 response remains unchanged and does not expose audit internals, provider identifiers, permissions, passwords, or secrets.

## Failure Events

Phase 08I now uses the existing `FAILURE` outcome for selected staff-invitation failures. These failure events are written outside the failed provider/database operation using safe internal reason codes only. They never contain provider response bodies, email addresses, bearer tokens, connection strings, or Supabase secrets.

## Supabase Boundary

Phase 08I uses the audit service for `USER_INVITED` success/failure and `USER_ACTIVATED` success events. The provider invitation and PostgreSQL transaction cannot be one distributed transaction, so the backend attempts best-effort provider-user cleanup when local linkage/audit fails. A cleanup failure produces a reconciliation-required result rather than automatically linking a provider identity by matching email.

## Phase 09 Review and Correlation Boundary

Every Express API request receives a server-generated UUID before JSON parsing and the identifier is stored in trusted request/response locals and returned as `X-Request-ID`. Client-supplied request identifiers are not accepted as authoritative audit identity. Existing CLI/bootstrap events may keep `request_id = NULL`.

The complete clinic audit trail is exposed only through:

- `GET /api/audit-events`
- `GET /api/audit-events/:auditEventId`
- `POST /api/audit-events/export`

The middleware sequence is authentication -> active application-user resolution -> RBAC resolution -> `audit.read` or `audit.export` enforcement -> audit review service. Dentist-only, Personnel, Patient, and System Administrator accounts are denied complete audit access by default.

The separate audit-review repository provides parameterized, deterministic newest-first list/detail/bounded-export reads. The insert repository remains insert-only. Review input validates supported filters, UUIDs, timestamps, pagination bounds, and export limits before PostgreSQL access. Safe public errors do not expose database/provider details.

Successful list/detail access writes `AUDIT_LOG_VIEWED`; successful CSV export writes `AUDIT_LOG_EXPORTED`. These events contain trusted actor UUIDs, the trusted request UUID, bounded result counts, and minimal safe filters. Audit review defensively redacts unsafe historical metadata recursively even if an unexpected row bypassed normal insertion validation. CSV output excludes authenticated-provider UUIDs and neutralizes spreadsheet-formula prefixes (`=`, `+`, `-`, and `@`) before CSV escaping.

Sensitive permission denials after successful authentication and application-user resolution append best-effort `AUTHORIZATION_DENIED` events containing only the permission code, safe branch context when relevant, and the trusted request ID. Audit-write failure never replaces the original 403 response.

## Deferred Audit Coverage

The backend still must not claim `LOGIN_SUCCEEDED`, `LOGIN_FAILED`, `PASSWORD_CHANGED`, or `PASSWORD_RESET_REQUESTED` for browser-to-Supabase flows it cannot truthfully observe. Passwords must not be routed through Express merely to create audit events.

Patient/Treatment/Appointment audit events remain with their protected V2 route cutovers. Attachment, Finance/Collectibles, Backup/Recovery, and MFA audit events remain deferred to their respective implementation phases. No audit UI/dashboard is part of Phase 09 beyond the protected API foundation.
